# DOGFOOD Threat Model

**Scope:** Current checkout's event submissions, judge evaluation, and all configured community-voting paths. This is a code-backed review of the implementation, not a penetration-test report or a claim that the competition entry is eligible. The official DOGFOOD threat-model bonus asks for voting/submission abuse, attacks stopped, and accepted risks; see [`plans-dogfood/00-official-requirements.md`](plans-dogfood/00-official-requirements.md).

## Assets and trust boundaries

- Submission records, revisions, event assets, custom answers, and the submission deadline.
- Judge assignments, track restrictions, evaluations, ballots, comments, and event results.
- User credentials, session tokens, event memberships, and audit records.
- Public gallery and API responses, which must not reveal drafts, private answers, peer evaluations, or active voting tallies.

The browser is untrusted. API handlers resolve an actor from a session cookie, and domain services enforce permissions and event/project relationships. Database uniqueness and foreign-key constraints backstop selected invariants. A signed-in account is an identity boundary, not proof of a unique real person.

## Controls present in this checkout

| Late or premature submission | `assertSubmissionWindow` checks event state and server time on create, edit, and submit paths. A locked project cannot be changed. Required title, description, and custom answers are validated when submitted. | `packages/submissions/src/domain.ts`, `packages/submissions/src/service.ts`; `tests/integration/submissions.test.ts`, `tests/integration/submissions-lock.test.ts`. The checker’s submission probe can fail schema validation before it reaches deadline logic; see `PLAN.md`. |
| Duplicate project creation by one team | A database uniqueness conflict is mapped to a team-already-has-project error. | `packages/submissions/src/service.ts`; `tests/integration/submissions.test.ts`. This limits projects per team, not coordinated teams or accounts. |
| Draft/private project exposure | The voting ballot selects only submitted or locked projects in eligible event states. Tokens are 32 random bytes, and email invitation hashes are stored instead of raw tokens. | `apps/web/app/api/v1/events/[eventId]/voting/ballot/route.ts`, `packages/voting/src/service.ts`, `packages/db/src/schema/voting.ts`. Email invitation addresses are labels only: ownership is not verified and the app does not send mail. |
| Repeat voting under one identity | Unique indexes allow one vote per account, email invitation credential, or open-link token per event. Open-link tokens are minted server-side and only their SHA-256 hash is stored; a well-formed token the server never issued cannot load a ballot or vote. Duplicate inserts fail and are audited. | `packages/db/src/schema/voting.ts`, `packages/voting/src/service.ts`; `tests/integration/voting.test.ts` ("rejects well-formed open-link tokens the server never minted"). A client that clears its cookie gets a new token, so this is one vote per minted token, not per person; see the minting cap below. |
| Project-team self-voting | Any signed-in actor is checked against the selected project's team before vote insertion, regardless of configured mode. Blocked attempts are audited without consuming a vote rate bucket; repeated denials by one account are deduplicated per minute to limit audit/webhook amplification. | `packages/voting/src/service.ts`; `tests/integration/voting.test.ts` covers authenticated, open-link, and email-gated cases. Anonymous callers have no account identity to check. Deduplication limits persisted audit events, not request traffic. |
| Open-link identity farming | New open-link identities are minted only by the server, with hourly caps per event (`DOGFOOD_VOTING_LINK_EVENT_LIMIT_PER_HOUR`, default 5,000) and, behind a trusted proxy, per network prefix (`DOGFOOD_VOTING_LINK_NETWORK_LIMIT_PER_HOUR`, default 200). Returning browsers keep their token without consuming the cap. The first refusal per bucket and window is audited as `vote.link.network_rate_limited` / `vote.link.event_rate_limited`. | `packages/voting/src/service.ts`, `apps/web/app/api/v1/events/[eventId]/voting/ballot/route.ts`; `tests/integration/voting.test.ts` ("caps open-link identity minting…"). Distributed clients across many networks can still collect up to the event cap; the event cap can also block legitimate newcomers during a spike. |
| Vote/comment write flooding | Authenticated writes use per-account/event/action minute buckets; all votes also use a configurable event-wide hourly attempt cap (default 10,000). Anonymous votes can additionally use a configurable network-prefix hourly cap (default 2,000) when trusted proxy IP handling is enabled. The network key is an HMAC of IPv4 `/24` or IPv6 `/64`; raw IPs are not stored. Repeated rate-limit denials are deduplicated per hashed limiter identity/action/window so a blocked client cannot create an unbounded audit and webhook stream. | `packages/voting/src/service.ts`, `packages/db/src/schema/voting.ts`, `apps/web/app/api/v1/events/[eventId]/votes/route.ts`; `tests/integration/voting.test.ts`. Network throttling is opt-in and requires `DOGFOOD_TRUST_PROXY_HEADERS=true` plus `DOGFOOD_VOTING_ABUSE_SECRET`; configure the reverse proxy to overwrite `X-Real-IP`. These are volume limits, not person identity checks. |
| Late archive import into an event under judging or published | Organizer imports are rejected once event judging has started, before archive records are inserted. | `packages/exports/src/bulk-projects.ts`; `tests/integration/bulk-projects.test.ts`. The import format still does not restore events, teams, tracks, or binary assets. |
| Ballot-order influence | Project order is shuffled with Node's cryptographic `randomInt` on each ballot request. | `packages/voting/src/service.ts`. Randomized ordering does not establish that each person saw only one order or eliminate strategic voting. |
| Strategic tally influence during voting | While the event is in `JUDGING` or the configured close time has not passed, results require organizer permission. Results become readable to authenticated users after the configured close time. | `packages/voting/src/service.ts`; active-window and close-time tests in `tests/integration/voting.test.ts`. Organizers can see tallies while voting is active by design. |
| Unauthorized audit access | Voting audit reads require an authenticated actor and event-audit permission; inactive organizer membership is denied. Vote audit rows intentionally omit actor, resource, and metadata identifiers. | `apps/web/app/api/v1/events/[eventId]/voting/audit/route.ts`, `packages/audit`, `tests/integration/voting.test.ts`. Audit history is an application log, not tamper-evident external evidence. |
| Judge reads or scores outside assignment/track | Evaluation services require the assigned judge, enforce event and track scope, reject a judge evaluating their own team's project, and preserve judge-to-judge score isolation. | `packages/judging/src/service.ts`, assignment and evaluation routes; `tests/integration/judging/assignment-isolation.test.ts`, `assignment-guards.test.ts`, and `evaluation.test.ts`. The official checker verifies its own-score, peer-score, participant-denial, and export probes only. |
| Assignment manipulation after results | Assignment generation previews are checked against current project/track/capacity state before commit; assignment and recusal actions are audited. | `packages/judging/src/service.ts`; `tests/integration/judging/assignment-generation.test.ts`, `assignment-guards.test.ts`. Organizers remain trusted to choose assignments and judges. |
| Forged or silently revoked public judge record | Issuances and revocations are append-only rows with Ed25519 signatures over canonical payloads. Public verification checks signature integrity separately from issuer trust; trust is true only for a key fingerprint configured independently in `JUDGE_RECORD_TRUSTED_KEY_FINGERPRINTS`. Revocation returns a signed status receipt without exposing the revoked payload. The issuer publishes its active key fingerprint and trust pins at `/.well-known/dogfood-judge-records.json`, and `scripts/verify-judge-record.ts` re-checks a record's hash, signature, and issuer pin itself, ignoring the server's own `issuerTrusted` claim. | `packages/judging/src/public-record-ledger.ts`, `packages/judging/src/public-record-ledger-crypto.ts`, `packages/db/src/schema/judgeRecords.ts`; `tests/integration/public-judge-record-ledger.test.ts` and crypto unit tests. The well-known document is only as trustworthy as the origin's TLS; pass `--pin` to the verifier to use an out-of-band fingerprint. A trusted deployment pin and private-key custody are required; no official external trust authority or automated key-rotation protocol exists. |

## Accepted risks and unsupported defenses

These risks are accepted by the current implementation; they are not represented as solved:

1. **Sybil voting and ballot stuffing.** Authenticated access limits one vote per account, not person; email is not verified at registration. Open-link access is deliberately public. Clients can no longer fabricate identities, because tokens must be server-minted, but a client can clear its cookie and ask for a new one. That is bounded by the per-network and per-event minting caps, and votes have separate event-wide and trusted-network caps. These limit volume, but distributed networks can bypass network caps, and an event cap can throttle legitimate high-volume participation. The network cap only works when deployment enables trusted proxy handling and configures the proxy to overwrite `X-Real-IP`; untrusted client headers must not be enabled as a source. Email-gated invitations remain manually shared bearer links; the stored address is not verified and no mail is sent. There is no CAPTCHA, identity proofing, or event-wide anomaly review. These controls add volumetric friction but do not establish unique people or prevent Sybil voting.
2. **Account takeover and credential abuse.** Password authentication and opaque server-side sessions are used, with only a hash of the session token stored and a 30-day session expiry. The inspected flows show no email verification or multi-factor authentication. Protection against password spraying, credential stuffing, and compromised devices is not established by this threat model.
3. **Cutoff race at submission deadline.** Deadline checks use server time, but `submitProject` performs its check before the transaction that changes project state. A request that passes the check just before cutoff may commit just after it; strict serialization of submission against the event deadline is not established. The published checker’s 4xx probe is insufficient to prove this behavior.
4. **Judge collusion and conflicts outside the app.** Assignment isolation prevents ordinary cross-judge score reads, and same-team judges are blocked from evaluating their own team. The platform cannot prevent judges coordinating outside the service, recognizing authors, sharing screenshots, or using multiple identities. Organizer assignment decisions are trusted; the available recusal flow is an audit/review mechanism, not conflict-of-interest discovery.
5. **Scraping and public-content abuse.** Anonymous gallery content is intentionally public. No application-level public-read throttling, bot challenge, or scraping deterrent was found in the inspected gallery path. Published project material may be copied, indexed, or used for spam; public filtering protects drafts and private event states, not confidentiality of submitted work.
6. **Limited audit guarantees.** Voting actions and sensitive organizer changes have audit records, but the database-backed log has no cryptographic chaining, external append-only sink, or publicly verifiable integrity proof. Vote audit deliberately excludes voter identity, so investigators cannot attribute a ballot from that audit stream alone.
7. **Network/service availability.** Per-account write buckets do not stop distributed traffic or resource exhaustion. Reverse-proxy limits, monitoring, backup/restore, and production incident response are deployment responsibilities and were not validated here.
8. **Judge-record key trust and rotation.** A signature proves that its payload matches a private key only when the public key is trusted independently. Deployments must provision the expected fingerprint through a trusted channel and protect `JUDGE_RECORD_SIGNING_PRIVATE_KEY`; automatic key rotation and a competition-owned trust authority are not implemented.

## Operating assumptions and follow-up

- Keep authenticated-account as the documented default. Treat open-link and email-gated access as intentionally weaker modes; do not describe either as person-verified or Sybil-resistant. For deployments using anonymous modes, set `DOGFOOD_VOTING_ABUSE_SECRET`, enable `DOGFOOD_TRUST_PROXY_HEADERS=true` only behind a proxy that overwrites `X-Real-IP`, and tune `DOGFOOD_VOTING_NETWORK_LIMIT_PER_HOUR` / `DOGFOOD_VOTING_EVENT_LIMIT_PER_HOUR` (votes) and `DOGFOOD_VOTING_LINK_NETWORK_LIMIT_PER_HOUR` / `DOGFOOD_VOTING_LINK_EVENT_LIMIT_PER_HOUR` (new open-link identities). For higher-stakes events, disable anonymous modes or add an eligibility check and shared identity controls before relying on one-vote limits.
- Email invitations are bearer codes: organizers must share them through a trusted channel, and anyone receiving a forwarded link can vote. The typed email is not authentication.
- If cutoff semantics must be strict, serialize deadline changes and submissions in the same database transaction and test requests racing the close time.
- If public tallies must be hidden from organizers too, change the current policy explicitly; the application follows the published site role matrix, which lets organizers read raw scores and tallies at any stage.
- Treat this document as a snapshot. Re-check it after auth, submission-window, voting, assignment, or audit changes; the focused tests named above are evidence for code paths, not a substitute for a security test.
